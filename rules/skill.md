# Skill Rules

Rules that all workflow skills must follow. Include the mandatory ones in the `## CRITICAL RULES`
section of each skill.

---

## Mandatory Rules

### 1. Language

```markdown
**Language** - talk to the user in their language; what people of the product read in the product
language; git, code and agent documents in English (see [Language](.claude/specs/language.md))
```

- **Documents FOR Claude** (skills, specs, templates, rules, the verifier) → **English**
- **Messages to the user** → the language the user writes in (the product language until they write
  in their own words). Quote them in the skill in English, as templates.
- **Product documents GENERATED BY skills, for people** (Jiku, discovery, README, `docs/`,
  CHANGELOG) → the **product language** (`language` in `_jflow/project.yaml`, Spanish when unset), with
  the structure of the [Language](../.claude/specs/language.md) spec
- **Git** (commits, MR/PR text, branch names, test names) → **English**
- **The definition** (`_jflow/prd/`…) → structure in **English**, content in the product language
- **Documents GENERATED BY skills, for agents** (`AGENTS.md`, `CLAUDE.md`) → **English**
- **Code and contract identifiers** (tables, columns, enums, paths, fields, `operationId`s) → **English**

### 2. Deterministic work goes through `jflow.py`

```markdown
**Deterministic work through `jflow.py`** - {the commands this skill uses}
```

The agent decides and interprets; everything repeatable is a command of
`.claude/scripts/jflow.py`: transcribing, indexing, checking, allocating IDs, loading context, moving
statuses, creating branches, computing coverage and evidence, writing the MR/PR text, talking to Jiku.
A skill never describes in prose a procedure the script can run. If a skill needs a new deterministic
operation, add it to the script (`.claude/scripts/jflowlib/`), standard library only.

### 3. Content to files, not to chat

```markdown
**Do NOT dump content in chat** - Save to file, show a summary, let the user review the file
```

Interactive skills also follow **save first, then validate**: write the part, run its check, notify,
then ask for confirmation with `AskUserQuestion`. A skill whose parts depend on each other and end in
one write (`jflow-spec`, the base specification of `jflow-product-scaffold`) asks only the decisions as it
goes and confirms the whole draft once, before writing. Every review request gives the file's
absolute path as a link: the user cannot review a file they cannot find.

### 4. Fixed locations

Every product is a monorepo with the layout of the
[Product Definition](../.claude/specs/product-definition.md) spec. Skills use those paths directly;
there is no files index.

## Frontmatter

```yaml
---
name: skill-name                 # = folder name, lowercase, hyphens
description: One line, shown in autocomplete
allowed-tools: "Read, Write, Edit, Bash, Glob, Grep, AskUserQuestion"
argument-hint: "[jiku-requirement-id]"   # only when the user knows what to pass
---
```

- `allowed-tools`: only what the skill needs. Read-only skills: `"Read, Glob, Grep, Bash"`. Skills
  that delegate add `Agent`; skills that research add `WebSearch, WebFetch`.
- No `model:`: skills run on the session's model.
- Jiku ids are plain numbers: `812`.

---

## Pre-injection (`` !`command` ``)

Only lightweight checks (`ls`, `grep -H "^status:"`, `git status --porcelain | head`). Never `cat` a
document: read it at runtime when the step needs it.

---

## Autonomous and interactive skills

| Kind | Skills | Rule |
|---|---|---|
| Interactive | `jflow-product-discover`, `jflow-spec`, `jflow-release` (one confirmation) | The user decides every rule; what is written is confirmed with `AskUserQuestion` (per section in `jflow-product-discover`, the whole draft once in `jflow-spec`) |
| Autonomous | `jflow-product-scaffold`, `jflow-product-brownfield`, `jflow-build`, `jflow-fix` | Only the git and state checks at the start may ask (`jflow-product-brownfield` also asks once, in one round after its survey: the values only the user has and the behaviors to confirm). After them, never ask about the process. `jflow-build` asks a large gap the specification does not decide (options and a recommendation, all at once) and writes the answer to the specification in Jiku before building it; it is never filled in silently |
| Read-only | `jflow-status` | Never write, in the repo or in Jiku |

Every skill that works on a requirement checks the git state (`jflow.py git-check`) and the Jiku state
at the start, and warns and asks when they are not the expected ones.

Autonomous skills that produce code or the definition always end with the `jflow-verifier-agent` subagent: they are done only with
its APPROVED verdict. Each new verifier gets the previous findings; each fix covers every place of the kind the finding names, not only the one it cites; they stop when a finding survives three fixes or after eight rounds, and report honestly that the work is not done.
